# WordTower 无界面数据模式（Headless）改造方案

状态：方案已确认，待实施
日期：2026-10-22

## 一、改造目的

游戏画面完全由数据支撑：棋盘、兵、血量、波次、经济全部来自全局状态 `G`，canvas 只负责把它们画出来。此前 agent 测试游戏只能靠截图拼凑画面，低效且失真。

本次改造把「数据」和「画面」解耦：

1. **读数据 = 看画面**。agent 通过结构化快照了解战局，每格有坐标、状态、对象，不依赖图像。
2. **操作数据 = 操作游戏**。agent 通过命令（摆兵、开波、推进时间）控制游戏，等价于人类的点击和拖拽，但精确、可批量、可复现。
3. **对局全程可记录**。每局、每一步操作都存档，可回放、可复盘、可回归测试。
4. **规则零差异**。headless 跑的是与画面版完全相同的代码，人用画面玩、agent 用数据玩，同一套规则——与「联机与单机同一套规则」铁律同源。

## 二、格子模型（沟通语言）

每个格子三要素，这是 agent 描述和验证战局的基本单位：

| 要素 | 内容 | 示例 |
|---|---|---|
| 坐标 | 列 `c`(0-7) + 行 `r`(0-7)，另有原始索引 `idx = c + r*8` | `(3,5)` |
| 状态 | `land` 可放置 / `path` 蛇形路 / `adu` 主公格；综合占用给出 `canPlace` | `land, canPlace:true` |
| 对象 | 格上的兵：种类、品阶、等级、血量、合成占格 | `{type:"弓", level:2, hp:80}` |

棋盘 8×8，上下两个半场（我方 `G.board` / 敌方 `G.enBoard`）各 64 格；行军中的兵不在格上，单独列表输出。敌方半场按镜像（对面视角）输出坐标并注明，与画面所见一致。

## 三、文件改动

### WordTower.html（两小块，不影响正常游戏）

1. 新增 `snapshotData()`：输出全量状态的结构化 JSON（见第四节）。
2. 文件末尾（IIFE 内）加出口：`window.__WT_HEADLESS__` 存在时，把内部 API（`G`、`newGame`、`step`、`startWave`、摆兵/合成/回收/征兵/商店/技能等）挂出去；否则什么都不发生。

### headless.js（新增，Node 运行器，零依赖）

- 读 WordTower.html → 抽 `<script>` → 注入桩层（canvas 2d 上下文用 Proxy、AudioContext、`requestAnimationFrame` 空转、localStorage 内存版）→ eval 加载同一份游戏代码。
- 逻辑函数里散落的 `sfx/floater/burst` 等渲染调用由桩层兜住，不改逻辑代码。
- eval 失败直接报错退出，不产出假数据。
- 两种运行方式：
  - **交互模式**：stdin 每行一条 JSON 命令，stdout 回 JSON——agent 逐步调试。
  - **脚本模式**：`node headless.js 场景.json` 一次跑完输出结果——回归测试。

## 五、命令集

| 命令 | 作用 |
|---|---|
| `newGame {seed, aiLevel}` | 开新局；seed 固定 → 地图/波次/征兵/商店完全可复现 |
| `snapshot` | 读全量状态 |
| `place {hand, c, r}` | 手牌摆兵（失败自动放回，返回 `ok:false`） |
| `move {from, to}` | 盘上移动 / 拖叠合成 |
| `fuse {a, b}` | 兵营内两张牌合成 |
| `recycle {c, r}` | 遣散守军按 `recycleValue` 折馒头 |
| `road {hand}` | 手牌兵上路排队（等价拖到路格） |
| `enlist` | 征兵刷新 5 格手牌 |
| `shop {buy id}` / `shop {close}` / `useActive {slot}` | 商店与技能 |
| `tick {sec}` / `tick {to}` | 按 0.1s 固定步长推进时间；商店冻结时间需显式 close（与真人一致） |
| `startWave / pause / set` | 辅助命令；`set` 白名单改数值（测试用） |

## 六、对局记录（存档）

游戏由数据支撑，因此**一局游戏 = 种子 + 操作序列**。由于模拟确定性（mulberry32 + 固定步长），记录这两样即可完整复现一局。

### 记录内容

- **开局**：`newGame` 时的 `seed`、`aiLevel`、时间戳。
- **每步操作**：每条命令按序追加到本局记录，附当时游戏内时间 `t`（如 `tick 5` 之后 t=5.0）。
- **终局**：胜负结果、总时长、双方存活。

### 存储方式

- 运行目录下 `records/`，一局一个文件：`records/2026-10-22_2130_seed123.json`。
- 格式为 JSON Lines：首行开局信息，中间每行一条操作，末行结算。写文件用追加方式，每条操作落盘一次，崩溃也不丢步骤。
- 快照不存档：确定性保证「开局信息 + 操作序列」可重放出任意时刻的完整状态，需要时回放即得。

### 记录用途

1. **复现 bug**：拿问题对局的记录文件重放，逐步核对哪一步之后状态不符。
2. **回归测试**：历史对局批量重放，改了数值/逻辑后跑一遍，确认关键局面不变。
3. **复盘分析**：直接读操作序列 + 按需重放取快照，分析 AI 策略、平衡性。
4. **录像回放**（远期）：画面版可读同一条记录，按时间轴重现整局。

## 七、实施步骤与验收

1. `WordTower.html` 加 `snapshotData()` 与 headless 出口；`headless.js` 桩层 + 命令循环。
2. 对局记录：`records/` 落盘、重放命令 `replay 记录文件`。
3. 验收标准：
   - `node headless.js` 跑通一局完整人机对战：newGame → 摆兵 → tick 至终局，结果与画面版同 seed 一致。
   - 任意时刻 `snapshot` 的数据与画面显示一致（棋盘、手牌、血量抽查）。
   - 一局记录文件重放后，终局结果与原局相同。
4. 远期扩展：脚本模式批量回归、联机双端对跑同步验证。

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| 逻辑函数内嵌渲染/音效调用 | 桩层兜住，不改逻辑代码 |
| eval 整个 IIFE 环境差异 | 缺失全局对象全部补桩；失败即报错退出 |
| 确定性被破坏（浮点/遍历顺序） | 固定 0.1s 步长；重放结果不一致视为 bug 修掉 |
| 正常游戏受影响 | 出口仅在 `window.__WT_HEADLESS__` 已设置时激活，画面版零变化 |

## 九、实施结果（2026-10-22 完成）

- `WordTower.html`：新增 `snapshotData()`、`recycleCell()`、`__api` 补导出；`newGame(seed)` 接受种子。
- **玩法随机全部种子化**：新增全局 `gRnd`（有种子时 = mulberry32(seed)），征兵/字池/商店/AI 抽牌/来兵等 15 处玩法随机从 `Math.random()` 换成 `gRnd()`（视觉粒子与音效随机保留原样）。无种子时 `gRnd = Math.random`，行为分布不变，正常游戏零差异——一套规则，多种呈现。
- `headless.js`：桩层（canvas Proxy/AudioContext/rAF 空转/DOM）+ 三种模式 + 存档。
- 已验证：同 seed 同操作两遍 → 快照逐字节相同；存档重放 → 结果与终局快照完全一致；完整对局跑通（newGame → 征兵摆兵 → tick → 商店 → 胜负判定）。
- 快速上手：
  ```
  printf '%s\n' '{"op":"newGame","seed":42}' '{"op":"enlist"}' \
    '{"op":"place","hand":0,"c":3,"r":1}' '{"op":"tick","sec":10}' '{"op":"snapshot"}' \
    | node headless.js
  ```

## 十、对局录制与回放（画面版，2026-10-22 完成）

数据支撑画面，也就能记录整局。落地方案：

### 记录什么

**一局 = 种子 + 输入事件**。不存画面，也不存每帧盘面：

- 每局开打（备战那一刻）自动生成种子，地图/AI/征兵/商店全部由它决定。
- 玩家的每次按下 / 移动 / 抬起记录为 `[逻辑步号, 类型, x, y]`（逻辑坐标，与窗口大小无关）。
- 一局约 100~300 个事件，几十 KB；`localStorage` 存最近 10 局。

### 为什么能一模一样

- 逻辑改为**固定 1/60 秒步长**（积攒真实时间补齐，渲染仍逐帧）——同样的步数推进同样的状态。
- 所有玩法随机走 `gRnd`（种子驱动），视觉粒子/音效随机与局面无关。
- 回放 = 同种子重新开局，在录下的步号上喂回同样的输入点。规则同一套，输入同一份，结果必然一致。

### 回放入口

- 结算页新增「回放本局」按钮（单人；该局有录像才出现），点开以 2 倍速重演整局。
- 回放中：左上角 `回放 ×2`，右上角「退出回放」；真实点击被忽略，键盘暂停失效。
- 回放结束自动回到结算页，可再次回放或再战一局。

### 边界

- 联机（PvP）暂不录制：需要两端事件合并，留待后续。
- 作弊类直接改数值（`set` 等 headless 命令）不会进录像，回放自然对不上——正常游戏不存在这种情况。
- localStorage 不可用（隐私模式）时自动关闭录制，不影响游戏。

### 验证（headless 驱动真实指针事件）

`/tmp/replay_test.js`（基础）、`replay_test2.js`（多次摆兵/上路/暂停/结算按钮）、`replay_test3.js`（4 次商店含关闭操作）：
均验证「实时对局的终局快照」与「回放后的终局快照」**逐字段完全一致**。

## 十一、对局记录页与自动清理（2026-10-22 完成）

- 首页新增「对局记录」入口 → 独立记录页：按时间倒序列出每局（模式 · 难度、日期、胜负、时长/波次/操作数），点一条即从头回放；播完或退出都回到记录页。
- 存档自动清理（`REC_MAX` / `REC_MAX_BYTES`）：条数超 20 局或总量超 2MB，从最旧的开始丢；localStorage 写满再逐局丢弃重试，最近的几局总保得住。
- 结算页回放入口不变；两条入口共用 `startReplay(rec, back)`，`back` 决定播完回哪。
